============================================================
1. OBJECTIF GÉNÉRAL DU MOD
============================================================

Le mod permet de personnaliser les fermes de Farming Simulator 25 avec :
- une couleur de ferme personnalisée ;
- un logo de ferme personnalisé ;
- affichage du logo/couleur dans les menus, listes de fermes, carte, joueurs, hotspots, terres, etc.

Le mod est déjà publié sur ModHub dans une version précédente.
La version actuelle en développement ajoute surtout la possibilité d'importer des logos personnalisés depuis le dossier utilisateur.

À terme, le but est que les logos importés deviennent réellement liés à la sauvegarde / au serveur :
- un administrateur importe un DDS une seule fois ;
- le logo est enregistré côté serveur / sauvegarde ;
- le serveur peut redémarrer sans perdre le logo ;
- les joueurs connectés reçoivent automatiquement ce logo ;
- un nouveau joueur qui rejoint plus tard reçoit aussi le logo ;
- aucun joueur ne doit avoir à copier manuellement le DDS dans son propre dossier ;
- le fonctionnement doit être compatible avec un serveur dédié type VeryGames.

Une fois cette partie terminée, l'étape suivante est une vraie fenêtre de sélection visuelle des logos :
- bouton "Sélectionner logo" ;
- grille de miniatures ;
- environ 4 logos par ligne ;
- une seule longue page avec scroll vertical ;
- pas de pagination ;
- clic sur le logo puis confirmation ;
- logos intégrés + logos personnalisés dans la même liste.

2. ÉTAT ACTUEL — CE QUI FONCTIONNE DÉJÀ
============================================================

Le ZIP actuel contient principalement :
- modDesc.xml
- scripts/farmIconColor.lua
- les textures/logos intégrés
- les fichiers XML/l10n habituels

Le fichier principal est :
scripts/farmIconColor.lua

Fonctionnalités validées en jeu :

A. Logos personnalisés locaux
Le dossier utilisé est :

Documents\My Games\FarmingSimulator2025\
modSettings\FS25_farmIconColor\customLogos\

Les logos sont des fichiers DDS, par exemple :
Domaine3Epis.dds
TerraPro.dds
LAbeilleCool.dds

Spécifications utilisées :
- 256 x 256
- DDS
- BC3 / DXT5 avec alpha
- fond transparent
- blanc pur #FFFFFF lorsqu'on veut permettre la recoloration par la couleur de ferme
- mipmaps recommandés

B. Import dynamique
L'administrateur peut ajouter un nouveau DDS dans customLogos pendant que le jeu est lancé puis appuyer sur INSERT / Importer.

Le scan dynamique fonctionne.

C. Bouton "Importer"
Le bouton visuel dans la fenêtre de modification de ferme fonctionne :
- clavier INSERT ;
- clic souris sur le bouton.

Le clic souris a nécessité un hook manuel sur mouseEvent, car le bouton cloné n'était pas correctement déclenché avec le système GUI standard.

NE PAS casser cette partie.

D. Plusieurs logos
L'import de plusieurs logos en même temps fonctionne.

E. Ordre
Lors d'un import manuel pendant la session, les nouveaux logos sont ajoutés à la suite des logos déjà enregistrés.

Important :
au redémarrage complet, l'ordre dépend encore du scan local trié par nom de fichier.
Une future persistance du catalogue serveur devra conserver l'ordre définitif.

F. Sauvegarde des paramètres de ferme
Le mod sait déjà sauvegarder/restaurer :
- couleur de ferme ;
- identifiant/nom du logo sélectionné.

Le stockage actuel de ces informations est principalement sous :
modSettings/FS25_farmIconColor/<clé_sauvegarde>.xml

Il existe aussi une logique de compatibilité legacy avec la sauvegarde.

G. Synchronisation réseau existante
Il existe déjà un événement :
FarmIconColorSyncEvent

Il synchronise :
- farmId
- couleur
- logoName

Il NE synchronise PAS le fichier DDS ni les données de l'image.

Le serveur rebroadcast les visuels et effectue des synchronisations périodiques.

7. TESTS DE LECTURE DU DDS DÉJÀ EFFECTUÉS
============================================================

IMPORTANT :
beaucoup de temps a déjà été consacré à tester les API GIANTS.
Ne pas refaire les mêmes hypothèses sans raison.

----------------------------------------
TEST 1 — io.open
----------------------------------------

Le runtime expose io.open, mais la lecture binaire utilisable n'est pas disponible comme attendu.

On ne peut pas faire simplement :
io.open(path, "rb"):read("*a")

La lecture complète du DDS par Lua standard n'a pas été obtenue.

----------------------------------------
TEST 2 — API GIANTS fichier
----------------------------------------

copyFile(source, destination, overwrite)
FONCTIONNE.

Le moteur peut copier le DDS en binaire sans le décoder.

getFileMD5 a été essayé, mais certaines signatures provoquaient des warnings.
Ne pas s'appuyer dessus aveuglément.

createFile(..., FileAccess.READ)
renvoie un handle 0 dans ce contexte.
Donc ce n'est PAS une lecture valide.

fileRead / readFile / getFileSize n'étaient pas disponibles comme fonctions globales utilisables.

En revanche :
createFile(..., FileAccess.WRITE) + fileWrite
fonctionnent pour écrire des fichiers.

----------------------------------------
TEST 3 — streams réseau
----------------------------------------

Le runtime expose notamment :
createStream
streamReadUInt8
streamWriteUInt8
streamWriteStream
netSendStream

ATTENTION :
un test utilisant :
writeBitVectorMapToStream()
puis
readBitVectorMapFromStream()

sur un stream mémoire créé manuellement a fait CRASHER complètement Farming Simulator 25.

Le crash survenait juste après :
streamSetReadOffset(0)

et avant/pendant :
readBitVectorMapFromStream()

Il n'y avait pas d'erreur Lua récupérable.
Le moteur natif tombait.

CONCLUSION :
NE PAS réutiliser readBitVectorMapFromStream() de cette manière.

----------------------------------------
TEST 4 — loadBitVectorMapFromFile
----------------------------------------

Étonnamment :
loadBitVectorMapFromFile()

accepte le DDS personnalisé.

Le DDS Domaine3Epis.dds est bien reconnu comme :
256 x 256.

getBitVectorMapPoint()
renvoie des valeurs.

Cela semblait prometteur.

----------------------------------------
TEST 5 — interprétation RGBA
----------------------------------------

Nous avons tenté d'interpréter les valeurs retournées comme des canaux :
0
8
16
24

Résultat :
FAUX.

Les PNG générés à partir de ces valeurs produisent des bandes rouges/noires et du bruit.

Les quatre canaux testés séparément donnent tous des motifs corrompus.

Exemple de statistiques observées :
- canal 0 : couverture ~37.6 %
- canal 8 : ~22.8 %
- canal 16 : ~37.0 %
- canal 24 : ~20.1 %

Aucun canal ne représente correctement le logo ni son alpha.

CONCLUSION :
BitVectorMap ne fournit pas simplement les pixels RGBA du DDS de la façon supposée.

----------------------------------------
TEST 6 — reconstruction DDS DXT5 directe
----------------------------------------

Dernier build actuel.

Hypothèse testée :
un DDS BC3/DXT5 256x256 possède un mip principal compressé de 65536 octets.

Or le BitVectorMap 8 bits retournait également :
256 * 256 = 65536 valeurs.

Nous avons donc essayé de traiter ces valeurs comme si elles étaient directement le flux BC3/DXT5.

Le mod :
1. lit les 65536 valeurs via BitVectorMap ;
2. fabrique un header DDS/DXT5 ;
3. écrit :
   generatedLogos/custom_domaine3epis_roundtrip.dds
4. demande à FS25 de charger ce nouveau DDS.

Résultat :
FS25 ACCEPTE le DDS reconstruit comme texture valide,
MAIS l'image affichée est toujours totalement corrompue.

Le log du dernier test contenait :

[FS25_farmIconColor][DDS-ROUNDTRIP]
source id=custom_domaine3epis size=256x256
mapBytes=65536
expectedBC3TopMip=65536
hypothesisMatch=true

Puis :
payloadBytes=65536
totalBytes=65664

Et :
reconstructed DDS texture load ... usable=true

Mais visuellement :
bandes / bruit rouge-noir, pas le logo.

CONCLUSION DÉFINITIVE :
les 65536 valeurs retournées par BitVectorMap NE SONT PAS les octets BC3/DXT5 bruts du mip principal.
La correspondance de taille était une coïncidence.

============================================================

Le serveur doit idéalement posséder un catalogue du type :

logoId
displayName
ordre
largeur
hauteur
format/version
taille payload
checksum/hash
payload image

Exemple conceptuel :

<farmIconColorCustomLogos version="1">
    <logo
        id="custom_terrapro"
        name="TerraPro"
        order="35"
        width="256"
        height="256"
        format="...">
        <data>
            ...
        </data>
    </logo>
</farmIconColorCustomLogos>

Ce XML n'est qu'un concept.
Il peut être remplacé par une meilleure solution si on trouve une méthode FS25 native plus propre.

12. SI UNE LECTURE DES DONNÉES DEVIENT POSSIBLE
============================================================

Architecture réseau recommandée :

1. admin importe ;
2. serveur valide que l'expéditeur est admin/master ;
3. logo normalisé avec ID sécurisé ;
4. taille limitée ;
5. données divisées en chunks ;
6. upload client -> serveur ;
7. serveur vérifie checksum/taille ;
8. serveur écrit le catalogue dans la sauvegarde ;
9. serveur annonce le catalogue aux clients ;
10. clients ne téléchargent que les logos manquants ;
11. données reçues reconstruites dans :
    modSettings/FS25_farmIconColor/cache/
12. logo enregistré dans self.logos ;
13. synchronisation du logoName continue avec le système existant.

Éviter de renvoyer 100 Ko de logo toutes les 5 secondes avec le sync périodique existant.

Créer plutôt :
- manifest/catalog event ;
- begin event ;
- chunk event ;
- end event ;
- éventuellement request event.

Exemple :
FarmIconColorCustomLogoManifestEvent
FarmIconColorCustomLogoBeginEvent
FarmIconColorCustomLogoChunkEvent
FarmIconColorCustomLogoEndEvent
FarmIconColorCustomLogoRequestEvent

Utiliser des chunks raisonnables (par ex. 8-16 KiB) si le payload passe par streamWriteString.

18. RÉSUMÉ DES ÉCHECS À NE PAS REFAIRE
============================================================

NE PAS supposer que :
- io.open("rb") donne les octets du DDS ;
- createFile(FileAccess.READ) fonctionne parce que la fonction existe ;
- BitVectorMap 32 bits = RGBA ;
- canal 0/8/16/24 = R/G/B/A ;
- BitVectorMap 8 bits = alpha ;
- 65536 valeurs = 65536 octets BC3 ;
- readBitVectorMapFromStream() est sûr sur un stream mémoire arbitraire.

Le test readBitVectorMapFromStream() a déjà provoqué un crash complet de FS25.
